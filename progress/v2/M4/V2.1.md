# V2.1 — Island lifecycle and placement

Implemented the first task in M4. M4 itself is not complete.

The default Windows launch now creates native Win32/DirectComposition island hosts using the renderer selected by the V0 fallback gate. The tray WebView2 is created when opened. Hosts stay shown, transparent, topmost, nonactivating and absent from the taskbar. This pass leaves them fully click-through; interactive hit rectangles and drag detection are V2.2.

Preferences extend the existing SQLite settings JSON, preserving v0.1 fields and defaults. Shape and Place controls save independently through Rust IPC. Settings include island visibility, floating/notch shape, Small/Standard/Large, Primary/Follow mouse/All/Specific and a remembered display identity. Unplugging a specific display temporarily falls back to primary without discarding its identity. Reattachment restores it.

Placement is a pure function of monitor bounds, work areas, effective DPI, top taskbar bounds and cursor. Real enumeration uses `EnumDisplayMonitors`, `GetMonitorInfoW`, `GetDpiForMonitor`, hashed monitor interface paths and `SHAppBarMessage(ABM_GETTASKBARPOS)`. Display/DPI/work-area/Explorer notifications reconcile hosts. A native mouse hook requests work only when crossing a monitor boundary; no JavaScript or render timer runs for the native idle island. Acceptance fixtures disable that hook and never move the real cursor.

The host's base is 720×460 logical, scaled by the explicit size preference and Windows DPI. Its bounds stay fixed across activity states; only configuration or monitor/DPI/work-area changes reposition or resize it. Integer percentages avoid a half-pixel rounding error: Large at 150% is 1242×794 physical pixels. Singleton modes reuse `island`; All uses `island-<monitorId>`.
